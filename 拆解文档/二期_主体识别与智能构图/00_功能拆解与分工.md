## 二、分工矩阵

### Claude Code 负责（核心算法与基础设施：C1–C6 → F1–F6）

**优势**：可直接执行多文件创建与重构、跑通 Vitest / typecheck 验证、擅长纯逻辑算法、数据契约、Worker 与存储底层。核心算法的正确性必须有单元测试兜底，适合由能自主验证的一方承担。

| 任务 | 功能点 | 内容 |
|---|---|---|
| C1 | F1 | 数据契约层：`src/core/subject/types.ts` + storage 扩展（subjects 对象仓、Blob 存取） |
| C2 | F3 | 蒙版后处理与边界框：`src/core/subject/mask.ts` + 单元测试 |
| C3 | F4 | 构图引擎：`src/core/composition/`（纯函数 + OffscreenCanvas 合成）+ 单元测试 |
| C4 | F2 | 浏览器端分割：onnxruntime-web 集成、模型加载与缓存、Worker 推理、进度事件 |
| C5 | F5 | Alpha 与量化专项：透明像素处理验证与修复 + 测试 |
| C6 | F6 | 核心集成：`detectSubjects` / `composePreview` 组装，protocol 扩展，与 pipeline 对接 |

### Cursor 负责（UI 与交互层：K1–K6 → F7–F12）

**优势**：IDE 内实时调试 UI、组件与 Canvas 交互迭代快、开发者在场可即时目检视觉效果。UI/UX 依赖人的目测反馈，适合在场交互式开发。

| 任务 | 功能点 | 内容 |
|---|---|---|
| K1 | F7 | 图片导入 UI 增强：上传状态、预检错误展示 |
| K2 | F8 | 主体选择 UI：候选展示、蒙版叠加、重试 / 无主体 / 多主体态 |
| K3 | F9 | 构图工作台：三栏布局、拖动缩放、参数面板、实时预览 |
| K4 | F10 | 背景选择与画布比例 UI |
| K5 | F11 | 手动补选 / 擦除画笔（P1，依赖 C1 契约） |

## 三、任务先后顺序（详细版）

### 3.1 先看懂一句话版本

> **两个人同时干活：Claude Code 从底层往上盖（先定数据格式 → 再写算法 → 最后组装），
> Cursor 从界面往下接（先做不依赖别人的导入页 → 再用假数据搭界面 → 等底层好了换真数据）。**
> 全程只需要在 3 个时刻对齐一次进度，其余时间互不等待。

### 3.2 全局顺序图（从左到右 = 时间先后）

```
时间 ─────────────────────────────────────────────────────────────────→

Claude Code:  [C1 契约] → [C2 蒙版] → [C3 构图] → [C5 Alpha] → [C6 集成] → 修集成问题
                        ↘ [C4 分割（先冒烟后工程化）] ↗
                              ↑ C4 建议拆两步：C1 一完成就先花半天
                                做模型下载+单图冒烟，再回头补工程化

Cursor:       [K1 导入UI] → [K2 主体选择] → [K3 工作台] → [K4 背景] → [K5 画笔] → [K6 E2E]
                              ↑ 用假数据        ↑ 用假数据      ↑            ↑
                              （等 C1）        （等 C1）    （等 K3）  （等 C6 + K3~K5 全部完成）
```

- 上下两行是**并行的**：Claude Code 做 C2 时，Cursor 同时在做 K2，互不影响。
- 箭头 `→` 表示"必须等前一个完成"。
- 标注"等 C1"的地方：K2/K3 一开始**用假数据（mock）开发界面**，不用干等。

### 3.3 分阶段详解（每个阶段：谁在做什么、为什么、做完的标准）

#### 阶段 ①：启动（两个任务同时开工）

| 谁 | 任务 | 做什么 | 为什么先做 | 做完的标准 |
|---|---|---|---|---|
| Claude Code | **C1 数据契约** | 定义 Subject / Mask / Composition 等类型 + IndexedDB 存储扩展 | 这是**双方共同的"语言"**。没有它，Cursor 不知道界面该拿什么数据；它也是唯一阻塞别人的任务，所以绝对排第一 | 类型文件 + 存储测试通过，并写了一份 UI 方能看懂的契约说明 |
| Cursor | **K1 导入 UI** | 上传中 / 校验失败的各类提示界面 | 它只依赖一期已有的代码（`core/image/validate.ts`），**什么都不用等**，现在就能动手 | 各种错误路径有提示，正常路径进入"识别中"占位 |

#### 阶段 ②：并行开发（两人在各自的赛道上，互不等待）

| 谁 | 任务 | 做什么 | 为什么这时候做 |
|---|---|---|---|
| Claude Code | **C2 蒙版后处理** | 去噪、填孔、平滑、算主体边界框 | 纯算法 + 单元测试，不依赖模型也不依赖 UI，可以直接写 |
| Claude Code | **C3 构图引擎** | 裁切、缩放占比、定位、边距、背景合成 | 同上，纯函数；和 C2 互不依赖，顺序可以互换，哪个快先做哪个 |
| Cursor | **K2 主体选择 UI** | 原图 + 蒙版高亮、重新识别按钮、各状态展示 | C1 已完成 → 类型有了。**模型还没好没关系，用假蒙版数据先把界面搭起来** |
| Cursor | **K3 构图工作台** | 三栏布局、拖动缩放主体、参数面板 | 同理用假数据开发。这是整个二期最大的 UI 工程，越早开始越好 |

#### 阶段 ③：攻坚（Claude Code 攻最难的，Cursor 继续搭界面）

| 谁 | 任务 | 做什么 | 为什么这时候做 |
|---|---|---|---|
| Claude Code | **C4 分割模型**（重点） | onnxruntime-web 集成、模型下载缓存、Worker 内推理 | 唯一有**不确定性**的任务（模型效果好不好、跑得快不快，试了才知道）。建议拆两步：① C1 刚完成时先花半天做"模型下载 + 一张图冒烟"，尽早知道质量行不行；② 确认可行后再回来补完整的工程化（缓存、进度、错误处理） |
| Claude Code | **C5 Alpha 专项** | 保证透明像素不被当成黑色拼豆 | 独立小任务，可在等模型下载/训练等待间隙穿插完成 |
| Cursor | **K4 背景选择** | 透明背景（棋盘格预览）、纯色背景 | 接在 K3 后面做，工作量小；若 K3 提前完成可提前 |

#### 阶段 ④：第一次真正联调（双方会合）

| 谁 | 任务 | 做什么 | 为什么 |
|---|---|---|---|
| Claude Code | **C6 核心集成** | 把 C2/C3/C4/C5 组装成完整链路：识别 → 构图 → 生成 | 前置任务齐了才能组装；组装完，Cursor 的假数据就可以换成真的了 |
| Cursor | **切换真实数据** | K2/K3/K4 里 mock 的地方替换成真实契约调用 | 此时会暴露两边理解不一致的问题——**正常现象，当场解决** |

#### 阶段 ⑤：补齐交互（画笔）

| 谁 | 任务 | 做什么 | 为什么放这么晚 |
|---|---|---|---|
| Claude Code | 修 C6 联调暴露的核心层问题 | 按缺陷清单修 | 联调期主责 |
| Cursor | **K5 手动画笔** | 补选 / 擦除蒙版 | 画笔修的是**真实模型输出的蒙版**——假数据阶段做了也白做，所以必须等真数据通了再动 |

#### 阶段 ⑥：收尾

| 谁 | 任务 | 做什么 | 为什么放最后 |
|---|---|---|---|
| Claude Code | 支持修核心侧问题 | 配合 K6 发现的问题 | — |
| Cursor | **K6 状态收口 + E2E** | 核对全部 UI 状态清单 + Playwright 端到端测试 + 原功能回归 | E2E 要测**完整真实链路**，早了测不到；它也是上线前的最终关卡，天然排最后 |

### 3.4 三个同步点（除此之外不用互相等）

| # | 时刻 | 谁通知谁 | 内容 | 不对齐的后果 |
|---|---|---|---|---|
| ① | **C1 完成** | Claude Code → Cursor | 契约文件 + 说明文档已就位，K2/K3/K5 可以开工 | Cursor 无从下手或猜错数据结构，返工 |
| ② | **C3 + C6 完成** | Claude Code → Cursor | 真实数据源可用，K3/K4 从 mock 切换并开始联调 | Cursor 一直用假数据，最后才发现对不上 |
| ③ | **C4 冒烟结果出来** | Claude Code → Cursor | 蒙版质量 / 推理速度的初步结论（尤其若质量差，可能要换模型，影响 K2 的展示设计） | UI 做完了才发现模型输出和预期差距大，界面返工 |

### 3.5 关键路径与风险

- **关键路径（决定总工期的链）**：`C1 → C3 → C6 → 联调 → K6`。
  任何一环延期，整个上线时间后移——所以 C1 和 C3 优先级最高，别被其他小任务分心。
- **最大风险点：C4（模型）**。它不在关键路径的依赖链上，但不确定性最大。
  缓解办法：提前冒烟（见阶段 ③），如果量化模型质量不达标，还有两个退路——
  换稍大的模型（体积换质量），或降级为"人像优先"（MediaPipe 只支持人但效果好）。
- **联调期（阶段 ④）双方都别排新任务**，留缓冲处理两边理解不一致的问题。

## 四、目录边界（防冲突约定）

| 目录 | 归属 |
|---|---|
| `src/core/subject/`、`src/core/composition/` | Claude Code |
| `src/core/pipeline/`、`src/core/pattern/`（契约扩展）、`src/storage/`、`src/workers/` | Claude Code |
| `src/features/*`（新增 subject-panel、composition-workbench 等）、`src/components/`、`src/app/` | Cursor |
| `src/render/`（构图预览叠加层） | Cursor，需复用现有 canvas-renderer 模式 |
| 双方共享、只读 | `src/core/image/`、`src/core/sampling/`、`src/core/dithering/`、`src/core/palette/`、`src/core/quality/`、`src/state/`（扩展时先在契约文件中登记） |

> `src/state/` 默认归 Cursor 接线；若需新增 store 字段与 C1 契约相关，在 C1 中预先定义好类型，Cursor 只做绑定。

## 五、统一约束（双方共同遵守）

1. core 层保持纯 TypeScript、不依赖 DOM（OffscreenCanvas / ImageData 等 Web API 仅限 worker / render 边界使用）。
2. 沿用现有编码风格、ESLint / Prettier 配置；新增逻辑必须有 Vitest 单元测试（UI 组件除外，用 Playwright 覆盖）。
3. 耗时计算一律进 Web Worker，通过 `src/core/pipeline/protocol.ts` 的消息模式推送阶段与进度。
4. 透明区域不得被映射为黑色拼豆（验收红线）。
5. 不训练自有模型；模型文件作为静态资源按需加载，Cache Storage 缓存；确认模型许可。
6. UI 必须覆盖完整状态：上传中、处理中、成功、失败、无主体、多主体、预览、重新生成。
7. 不把二期功能（网格逐颗修改、画笔级专业编辑器、多主体智能组合）混入本次开发。
